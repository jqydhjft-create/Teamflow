# Codex 生产级应用工作流手册设计说明

**日期：** 2026-07-10

## 目标

制作一份中文 PDF 手册，帮助已经具备基本开发能力、但尚未形成稳定 AI 工程流程的开发者，建立一套可重复执行的 Codex 生产级应用交付方法。手册必须独立于具体项目和技术栈，适用于后端、前端、移动端、全栈、基础设施及常见企业应用开发。

读者完成阅读后，应当能够：

- 判断一个任务是否已经具备让 Codex 开始实现的条件；
- 为仓库提供恰当、持久且不过度的上下文；
- 将复杂需求拆成可验证、可审查、可回滚的小批次；
- 让 Codex 先调查和规划，再进行受约束的实现；
- 使用测试、静态检查、构建、浏览器验证和人工评审建立证据链；
- 管理安全、权限、依赖、数据库迁移、发布和回滚风险；
- 在速度与工程质量之间建立明确的控制点；
- 识别常见的 AI 生成代码失败模式，并及时纠偏。

## 内容定位

手册采用“生产生命周期工作流”作为主线，而不是按 Codex 功能菜单逐项介绍。正文从项目准备开始，沿着需求、调查、设计、计划、实现、验证、评审、发布和反馈闭环展开。Codex 的具体能力按照它们在工作流中的使用时机嵌入正文，并在附录中提供快速索引。

手册以通用工程原则为核心，不使用 TeamFlow 或其他现有仓库作为贯穿案例。必要示例使用简短、技术栈中立的虚构任务，例如“增加用户导出功能”“修复重复扣款”“为管理后台增加权限控制”。

## 文档结构

### 第一部分：建立正确的交付模型

解释生产级交付与代码生成之间的区别，明确 Codex 的职责、人类必须保留的决策，以及“上下文、约束、反馈、验证”四个控制变量。介绍最小可信闭环：调查、计划、修改、验证、审查。

### 第二部分：端到端标准工作流

按以下阶段展开：

1. 定义目标、范围、非目标和成功条件；
2. 准备仓库、开发环境和持久指令；
3. 让 Codex 调查现状并形成证据；
4. 比较方案，识别风险并确认设计；
5. 将设计拆成小步实施计划；
6. 通过测试或可运行检查约束实现；
7. 小批次修改并持续验证；
8. 系统调试、回归测试和浏览器验收；
9. 安全、数据、性能和可运维性审查；
10. 代码评审、变更说明和合并决策；
11. CI/CD、灰度发布、迁移和回滚；
12. 线上监控、事故反馈和知识沉淀。

每个阶段均包含五类信息：输入、推荐的 Codex 行为、人类决策点、必须形成的产物、进入下一阶段的退出条件。

### 第三部分：可复制的提示词模板

提供短小且可以替换变量的模板，覆盖：

- 新仓库和既有仓库调查；
- 需求澄清和验收标准；
- 方案比较与架构设计；
- 实施计划和任务拆分；
- 功能实现与缺陷修复；
- 测试驱动开发和回归测试；
- 系统调试和根因分析；
- 安全、性能和数据库迁移审查；
- 代码评审和发布前验收；
- 中断后的上下文恢复与工作交接。

模板强调目标、背景、范围、约束、验证命令、禁止事项和交付格式。避免冗长的角色扮演提示词。

### 第四部分：Codex 工作表面的选择

根据作用域说明何时使用一次性提示词、`AGENTS.md`、项目配置、Skill、Plugin、MCP、浏览器能力、Hook 和 Automation。重点回答“什么信息应该放在哪里”以及“什么情况下不应升级为更重的机制”。

产品事实以制作时获取的 OpenAI 官方 Codex 手册为依据。手册正文会把官方产品能力与作者总结的软件工程建议分开表述。

### 第五部分：高频失败模式与纠偏

覆盖直接要求生成整个系统、一次修改过多文件、上下文堆积、未经调查就重构、忽略现有约定、只听取模型的成功声明、只运行局部测试、把日志当根因、过度抽象、无边界的依赖升级、危险命令、权限过宽、数据库迁移不可逆、发布无回滚方案以及将秘密写入上下文等问题。

每个失败模式包含症状、根因、纠偏动作和预防规则。

### 附录

- 一页式端到端工作流；
- 生产就绪检查清单；
- 提示词速查表；
- `AGENTS.md` 通用模板；
- 缺陷修复任务模板；
- 发布前任务模板；
- Codex 能力选择速查表；
- 术语表和官方参考资料。

## 视觉与排版设计

成品使用 A4 纵向页面，正文目标为约 30 至 40 页。整体采用简洁的工程手册风格，确保屏幕阅读和黑白打印均清晰。

- 封面包含标题、副标题、版本日期和适用对象；
- 目录提供清晰的章节层级和页码；
- 章节页使用稳定的编号与视觉层级；
- 流程关系使用少量、紧凑的流程图或阶段图；
- 重复字段对比使用表格；
- 提示词使用等宽字体代码框；
- 风险、人工决策点和验证证据使用不同但可灰度区分的提示框；
- 页眉显示当前章节，页脚显示版本和页码；
- 控制单页信息密度，避免跨页断裂的标题、孤行和过大的表格；
- 中文字体必须完整嵌入或使用可稳定渲染的系统字体，避免方框和乱码。

## 内容原则

1. 以可执行步骤和检查条件为主，避免产品宣传。
2. 生产级不等于流程繁重；任务风险决定流程强度。
3. 明确区分“模型报告已完成”和“通过命令获得验证证据”。
4. 所有关键结论都尽量对应一个产物、命令、检查项或人工决策。
5. 不把任何单一技术栈、测试框架或部署平台描述为唯一正确选择。
6. 不建议把秘密、生产凭据、个人数据或不必要的大型文件放入上下文。
7. 不将 Codex 描述为无需监督的最终责任主体。
8. 不鼓励一次性重写、无验证的大范围重构或无法回滚的发布。

## 制作方式

1. 获取并检索当前 OpenAI 官方 Codex 手册，提取与工作表面、持久指令、Skills、MCP、Hooks、自动化和权限有关的事实。
2. 编写结构化中文原稿和参考资料列表。
3. 使用 ReportLab 生成 PDF，保持生成脚本最小、可重复运行。
4. 使用 PDF 文本提取检查页数、标题、关键段落和字符完整性。
5. 使用 Poppler 将全部页面渲染为 PNG，逐页检查溢出、重叠、乱码、断页和可读性。
6. 修复发现的问题后重新生成并再次执行完整检查。

## 验收标准

- PDF 能够打开并被标准 PDF 工具识别；
- 页数处于约 30 至 40 页的目标范围，若内容完整性需要，可在不牺牲可读性的前提下小幅偏离；
- 中文正文、标点和等宽代码均无乱码、方框或缺字；
- 无裁切、重叠、空白异常页、孤立标题或不可读表格；
- 包含完整端到端流程、工作技巧、提示词模板、失败模式和生产检查清单；
- 产品事实与制作时获取的官方 Codex 手册保持一致；
- 引用和官方链接为人类可读文本，不包含工具占位符；
- 最终文件经过文本检查和全部页面的渲染检查。

## 明确不包含的内容

- 不提供某一技术栈的完整示例应用源代码；
- 不比较 Codex 与其他 AI 编程产品的价格或排名；
- 不承诺无人监督即可安全上线；
- 不展开特定云厂商的部署教程；
- 不将未经官方资料确认的产品术语或能力写成确定事实。
